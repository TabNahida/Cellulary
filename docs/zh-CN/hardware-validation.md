# 硬件验证

[文档目录](README.md) · [English](../hardware-validation.md)

以下记录来自已安装厂商驱动的 Windows 电脑与真实设备，按日期描述所测硬件、固件及操作，不代表所有版本和运营商。设备标签仅用于本记录；不包含电话号码、SIM 标识、设备唯一标识和网卡地址。

## 测试设备

| 标签 | 模块 | 固件 | SIM |
| --- | --- | --- | --- |
| A | EC200A-EU/EUV1 | `EC200AEUV1HAR02A08M16` | 就绪 |
| E1 | EC801E-CN | `EC801ECNCGR07A03M02` | 就绪 |
| E2–E5 | 四个 EC801E-CN | `EC801ECNCGR07A03M02` | 未插卡 |

EC801E 的 USB VID/PID 为 `2C7C:0903`，EC200A 为 `2C7C:6005`，AT 接口为 `MI_03`。通过型号与固件查询区分产品，没有把同一模块的多个 USB 端口算作多台设备。调查期间 COM 端口名发生过变化，不能作为稳定设备身份。

## 2026-09-16 — 首轮集成

- 六个 AT 端口均有响应，`cellulary scan` 找到全部六台设备。无卡的 `+CME ERROR: 10` 映射为 SIM 未插入，模块本身仍在线。
- A 与 E1 已附着数据服务并有活动 PDP 上下文。A 注册在本地网络，E1 处于漫游注册。
- Windows 显示 A 的移动宽带接口已连接，并能列出现有配置文件。只读查询 `QCFG="usbnet"` 得到 A 为模式 `2`、E1 为模式 `3`；没有修改 USB 模式。
- E1 的 `QNETDEVCTL?` 返回 `3,1,1,1`，表示已有自动连接配置且 USB 连接处于已连接状态。本轮验证中 Cellulary 没有启停该既有会话。
- 真实 Web API 返回六台模块和两个就绪 SIM，与串口结果一致。
- 管理台在 1265×712 和 390×844 下检查通过。设备切换、数据读取、通话状态读取、错误显示及事件筛选均可用，没有整页横向溢出或浏览器控制台错误。
- A 接受 `CLCC` 并显示无活动通话，E1 对同一查询返回 `ERROR`，没有因此认定 EC801E 支持语音。

此阶段没有发送短信、发起或接听电话、修改 APN、激活/停用连接或切换系统路由。已有的“已连接”状态不等同于电脑实际互联网出口已验证。

## 2026-09-17 — EC801E 数据路径调查

### 能力与本机号码

A 通过 `CNUM` 返回了本机号码记录，本文不展示号码。E1 的 `CNUM` 仅返回 `OK`，没有号码记录；当前固件对 `CPBS=?`、`CMGF=?`、`CMGF?`、`CPMS?`、`CSCA?`、`CLCC`、`QGPS` 查询均返回 `ERROR`。

只读 SIM 文件调查进一步确认 E1 未保存号码：`CRSM` 读取 `EF_MSISDN` 元数据，显示五条记录、每条 30 字节；逐条读取后，五条记录的号码长度字段均为空（`0xFF`）。没有写入任何 SIM 记录。这张 SIM 的相应文件中没有本机号码，`CNUM` 或直接读取 `EF_MSISDN` 都无法恢复不存在的记录，应继续显示未知；这与数据服务是否正常独立。

短信命令失败与 E AT V1.3 对 EC801E 的限制一致。本次没有修复短信，也没有声明短信已支持；同样没有验证 EC801E 语音或 GNSS。

### 定位与恢复

E1 已在 LTE B3 频段漫游注册，并且已有 PDP 地址，因此观测到的问题不是找不到可用无线频段。

五个 EC801E 的 RNDIS 接口使用相同 MAC。通过 USB 父设备关联 AT 端口与网卡后，确认 E1 对应的主机网卡只有 APIPA/链路本地地址，而一个无卡模块对应的网卡获得了 DHCP 租约。仅凭网卡友好名称或重复 MAC 无法安全确认目标。

恢复时只释放已确认无卡网卡上的 DHCP 租约，只更新 E1 网卡的 DHCP。E1 随后获得有效租约和网关。没有更改主用或无关网卡，也没有改写模块持久配置。

### 实际互联网出口验证

请求显式选定 E1 的主机接口，避免把电脑其他连接的成功误认为此模块可用：

- 对 `example.com` 的 UDP DNS 查询通过 `IP_UNICAST_IF` 选定 E1，绑定源地址并使用模块分配的 DNS 服务器；响应事务 ID 匹配，返回成功（`rcode=0`）及两条答案。
- HTTP 请求使用 Windows `IP_UNICAST_IF`，接口索引按网络字节序传入，同时绑定源地址；远端返回 HTTP **301**。
- HTTPS 请求使用 `curl.exe --interface` 绑定 E1 的源地址，使用 Windows TLS 信任；`www.cloudflare.com` 返回 HTTP **200**。
- 另一次 Python HTTPS 请求同时使用 `IP_UNICAST_IF` 和源地址绑定，并开启证书校验。请求协商为 **TLS 1.3**，`www.cloudflare.com` 返回 HTTP **200**，进一步确认指定网卡的加密联网路径。

这些检查证明当时 DNS、HTTP 和 HTTPS 流量确实经过该 EC801E，没有测量吞吐、长期稳定性或故障切换。

重复 MAC 仍然存在。长期使用多个有卡模块，需要依据适用文档为每个模块配置唯一 MAC，或验证其他接口方案。本次恢复没有实施持久 MAC 修改或相关重启。
